# 決議：不支持在 VAR-System 中直接使用 TIME-System 設定變數值

## Context

此 RFC 針對 ISA-Level Gherkin 規格中 VAR-System（變數系統）與 TIME-System（時間轉換系統）的整合邊界做出設計決策。

在 ISA-Level Gherkin 規格中：

- **VAR-System** 提供變數操作機制：使用 `>contextKey` 定義要存入 scenario context 的變數名稱，使用 `<executionKey` 從執行結果中取值存入 context，使用 `$variableName` 引用 context 中的值
- **TIME-System** 提供時間轉換機制：使用 `@time("2025-11-04T08:00:00")` 將時間字串轉換為 timestamp (Long)，主要用於 API 呼叫時的參數轉換

## Problem

在測試案例中發現，目前的 helper 實作不支持以下用法：

```gherkin
When 創建訂單, call table:
  | >orderTime                   | amount |
  | @time("2025-11-04T08:00:00") | 1000   |

```

或

```gherkin
Given 準備一個訂單, with table:
  | >orderTime                   | amount |
  | @time("2025-11-04T08:00:00") | 1000   |

```

這種用法試圖在 VAR-System 的 `>contextKey` 中，直接在 data row 使用 `@time()` 表達式來設定變數值，而不是使用 `<executionKey` 從執行結果中取得值。

**核心問題**：是否應該支援在 VAR-System 的變數賦值中直接使用 TIME-System 表達式來設定變數值？

## Forces

在做出此決策時，必須考量以下約束和非功能性需求：

1. **結果導向 vs 過程導向**
    - ISA 規格設計哲學強調**結果導向**（outcome-oriented）的測試思維
    - 測試應該關注「系統產生什麼結果」，而不是「如何設定中間變數」
    - 變數應該從系統執行結果中取得，而不是手動設定
2. **ISA 規格的限制性**
    - ISA 規格應該保持一定的限制性，避免過度寬鬆的語法
    - 每增加一條寬鬆的語法規則，都需要考量在撰寫文化上可能遇到的問題
    - 過度寬鬆的語法可能導致測試規格品質下降
3. **變數系統的設計原則**
    - VAR-System 的設計目的是從**執行結果**中提取和保存動態產生的值
    - 變數應該反映系統的實際行為，而不是測試撰寫者的假設
    - 如果允許直接設定變數值，會破壞變數系統的語意一致性
4. **實際使用場景**
    - 創建訂單後，系統會自動產生 `createdAt` 等時間欄位
    - 這些時間值應該從執行結果中取得（使用 `<createdAt`），而不是手動設定
    - 如果需要特定的時間值，應該在 API 呼叫時使用 `@time()` 作為參數，而不是作為變數值
5. **維護性和可讀性**
    - 測試規格應該清晰表達「從系統取得什麼值」
    - 直接設定變數值會模糊「這是系統產生的值」還是「這是測試設定的假設值」的界限

# 決議

## 決議摘要

**決策：不支持在 VAR-System 的 `>contextKey` 中直接使用 TIME-System 表達式設定變數值。**

變數值必須透過 `<executionKey` 從執行結果中取得，而不是直接使用 `@time()` 或其他表達式設定。

## 解法設計

### 正確的用法

**場景 1：從執行結果中取得時間值**

```gherkin
When 創建訂單, call table:
  | >orderTime | amount |
  | <createdAt | 1000   |

```

- 使用 `<createdAt` 從執行結果中取得系統自動產生的建立時間
- 存入 context 的 `orderTime` 變數

**場景 2：在 API 呼叫時使用時間表達式**

```gherkin
When 創建訂單, call table:
  | orderTime                   | amount |
  | @time("2025-11-04T08:00:00") | 1000   |

```

- 在 API 呼叫的參數中使用 `@time()` 轉換時間值
- 這是 TIME-System 的正確使用場景：作為 API 參數的值轉換

**場景 3：如果需要保存 API 參數中的時間值**

```gherkin
When 創建訂單, call table:
  | >orderTime                   | amount |
  | <orderTime                    | 1000   |

```

- 前提：執行結果中必須包含 `orderTime` 欄位
- 如果執行結果不包含該欄位，說明系統設計有問題，應該修正系統設計而不是放寬語法

### 不支援的用法

```gherkin
# ❌ 不支持：直接在變數賦值中使用 @time()
When 創建訂單, call table:
  | >orderTime                   | amount |
  | @time("2025-11-04T08:00:00") | 1000   |

```

**原因**：

1. 違反了 VAR-System 的設計原則：變數應該從執行結果中取得
2. 這是過程導向的思維，而不是結果導向
3. 模糊了「系統產生的值」和「測試設定的假設值」的界限

### 實作層面的處理

- Helper 實作應該拒絕這種用法，或者在解析時忽略 `@time()` 表達式（保持向後相容）
- ISA-Linter 可以新增規則檢查，警告或禁止這種用法

# Resulting Context

## Pros

1. **保持設計哲學一致性**
    - 強化結果導向的測試思維
    - 變數系統語意清晰：變數 = 從系統執行結果中取得的值
2. **提高測試規格品質**
    - 測試規格必須反映系統的實際行為
    - 避免測試撰寫者設定假設值，導致測試與系統行為不一致
3. **維護 ISA 規格的限制性**
    - 避免過度寬鬆的語法導致規格品質下降
    - 保持語法規則的一致性和可預測性
4. **促進系統設計改進**
    - 如果測試需要某個時間值，系統應該提供該值
    - 促使開發者思考系統設計是否合理

## Cons

1. **靈活性降低**
    - 無法在變數賦值時直接使用時間表達式
    - 必須依賴系統執行結果中包含所需的時間欄位
2. **假設條件**
    - **假設**：系統執行結果中包含所需的時間欄位（如 `createdAt`、`orderTime` 等）
    - **如果違反**：如果系統設計不完善，執行結果中缺少某些時間欄位，測試撰寫者可能需要：
        - 修改系統設計，讓執行結果包含所需欄位
        - 或者使用其他方式（如透過 API 參數傳遞，然後從回應中取得）
3. **學習曲線**
    - 測試撰寫者需要理解 VAR-System 和 TIME-System 的正確使用場景
    - 需要區分「API 參數中的時間轉換」和「變數賦值」的不同用法

# 其他可能解法

## 方案 A：支援混合語法（已拒絕）

**描述**：允許在 `>contextKey` 的 data row 中直接使用 `@time()` 表達式

**優點**：

- 提供更大的靈活性
- 可以手動設定時間變數值

**缺點**：

- 違反結果導向的設計哲學
- 模糊變數系統的語意
- 可能導致測試規格品質下降
- 增加語法複雜度

**決策**：不採用此方案

## 方案 B：提供專門的語法（已拒絕）

**描述**：引入新的語法，如 `>orderTime=@time("2025-11-04T08:00:00")` 來明確表示「手動設定變數值」

**優點**：

- 語法明確，區分「從執行結果取得」和「手動設定」
- 保持 VAR-System 的語意清晰

**缺點**：

- 增加語法複雜度
- 仍然違反結果導向的設計原則
- 需要額外的實作和維護成本

**決策**：不採用此方案

## 方案 C：當前方案（已採用）

**描述**：不支持在變數賦值中直接使用 TIME-System，變數必須從執行結果中取得

**優點**：

- 保持設計哲學一致性
- 語意清晰
- 促進系統設計改進

**缺點**：

- 靈活性較低
- 需要系統設計支援

**決策**：採用此方案
